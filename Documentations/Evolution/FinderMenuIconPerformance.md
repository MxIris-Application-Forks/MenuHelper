# 访达菜单图标性能优化

## 动机

访达请求 Finder Sync 菜单时，只要启用应用图标，菜单项就会延迟出现；关闭图标后则能立即显示。原有缓存虽然避免了反复调用 `NSWorkspace` 获取图标，但缓存文件仍包含 `1024×1024` 像素的完整应用图标。扩展返回 `NSMenu` 时，这些图像需要随菜单一起跨进程传递，导致缓存命中后仍有明显延迟。

本机使用 15 个应用菜单项测得：旧缓存文件合计约 27.8 MB，近似归档后的菜单达到约 88 MB；真正缩成菜单所需尺寸后，归档负载约为 121 KB。

## 范围

- 为访达菜单增加独立的、小尺寸应用图标路径。
- 保留设置界面使用的高分辨率应用图标，避免放大菜单缩略图造成模糊。
- 将磁盘读取、应用图标获取和缩略图生成移出访达同步菜单请求路径。
- 对内存缓存和正在生成的任务状态增加同步保护。
- 移除进程内 `NSMenu` 缓存，避免首次占位图被长期保留；菜单本身很小，重新构建的成本远低于图像传输成本。

## 关键设计与取舍

菜单图标使用 `16×16` point 的逻辑尺寸，并只携带一个 `32×32` 像素位图表示，满足 Retina 显示需要。仅修改 `NSImage.size` 不会删除底层高分辨率表示，因此生成缓存前必须显式栅格化到目标像素尺寸。

设置界面继续通过 `displayIcon(for:)` 使用完整应用图标；访达菜单改用 `menuIcon(for:)`。内存未命中时，`menuIcon(for:)` 立即返回同样经过缩小的占位图，并在后台读取磁盘或生成真实缩略图，保证同步菜单回调不等待文件读取与图片处理。

磁盘缓存使用 `MenuIconCacheV2` 目录和版本字段。旧的 `IconCache` 目录只包含可重新生成的数据，会在后台删除。没有尝试复用旧缓存，因为读取和解码其中的大图本身就是需要消除的开销。

## 影响面

- 访达右键菜单和工具栏菜单使用小尺寸图标，跨进程负载显著降低。
- 新安装或升级后的第一次缩略图生成在后台完成；极早打开菜单时可能先看到占位图，之后的菜单请求会显示真实图标。
- 设置界面的图标质量不变。
- `Package.swift` 只用于直接编译共享缓存源码并运行回归测试，不改变 Xcode 应用和扩展 target 的依赖结构。

## 迁移与升级注意事项

升级后无需用户操作。应用会使用新版缓存目录，并在后台清理旧缓存。缓存内容全部是派生数据，删除后可以从已配置的应用重新生成。

回归测试需先更新 Swift Package 依赖，再使用隔离的构建目录运行：

```sh
swift package --package-path . --scratch-path /tmp/codex/SwiftPM/MenuHelper update
set -o pipefail
swift test --package-path . --scratch-path /tmp/codex/SwiftPM/MenuHelper 2>&1 | xcsift
```

这里使用 `swift test` 是因为当前 XcodeBuildMCP CLI 的 Swift Package 测试命令不能指定独立的 scratch path；直接使用它会与用户的默认 `.build` 目录共享产物。

测试永久约束以下行为：缓存图像只能包含菜单尺寸的位图表示；磁盘缓存不得重新保存完整应用图标；15 个不同图标组成的菜单归档必须小于 1 MB。
